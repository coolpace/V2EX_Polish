# 签到调度纵深防御设计

## 背景

2.5.5 中缺少账号身份的签到状态会在每次归一化时重建，并通过 `storage.onChanged`
再次触发调度，造成持续写入和 Service Worker 高 CPU。首轮修复已经让状态迁移保持
幂等，并对调度请求做了串行合并。

## 目标

- 没有已确认账号身份时，不允许自动签到或创建签到 alarm。
- 持久化的时间戳和调度状态必须经过校验，损坏值不能阻塞 alarm 或导致重试风暴。
- 同一上下文内的账号观察和签到状态写入按顺序执行。
- 用回归测试和性质测试固定以下不变量：
  - 同一状态再次归一化后保持幂等。
  - 当前奖期状态只迁移一次。
  - 自动调度最多创建一个有效 alarm。
  - 重复 storage 事件不会产生额外写入。
  - 无账号身份时不会自动发起网络请求。

## 非目标

- 不改变 V2EX 的签到规则、奖励日或失败退避策略。
- 不在本次改动中识别 Cookie 对应的真实账号。
- 不重构页面内容脚本或主题逻辑。

## 方案

采用纵深防御：

1. 调度层要求账号身份已确认，匿名状态只允许用户显式手动触发。
2. 归一化层校验 `targetAt`、`nextActionAt`、`nudgeEligibleAt` 等持久化时间字段，
   丢弃非法值并重新建立有效计划。
3. 账号观察和签到状态读取/写入通过共享串行队列执行；网络请求不占用该队列，
   账号切换仍可在请求期间及时推进 revision。
4. 后台集成测试模拟自身 storage 事件、事件风暴、遗留匿名 alarm 和损坏时间值，
   纯函数测试使用确定性生成的状态验证归一化不变量。

## 风险

- 无身份时不再自动发起签到，首次使用时需要访问 V2EX 页面或手动触发，这比误签到
  或请求风暴更安全。
- 串行队列只在单个 background 上下文内有效；跨浏览器上下文仍依赖持久化状态和
  revision 校验。
- 如果 Cookie 在没有任何 V2EX 页面上报新用户名时切换，后台无法主动识别；
  下一次页面身份观察会重置状态，但本次正在进行的请求仍可能短暂使用新 Cookie。
